## 1. Executive Summary

Introductory programming units enrol several hundred students per semester, and lab sessions are where most practical learning happens. In a two-hour lab, one tutor typically supports 25–30 students, and much of that time is spent on the same recurring difficulties: misunderstood error messages, off-by-one loops, and confusion between returning and printing a value. Students who wait too long for help disengage, and the evidence that early struggle predicts later failure in introductory programming is well established (Denny et al., 2024).

General-purpose AI assistants are now widely available to students, but they tend to produce complete solutions on request. Educators have raised concerns that this short-circuits learning, particularly for novices who cannot yet evaluate the code they receive (Kasneci et al., 2023; Prather et al., 2023).

This proposal presents **CodeCoach**, an AI agent that sits beside the lab exercise and responds to a stuck student with a graded sequence of hints. CodeCoach reads the exercise specification, the student's current code and the latest error or test output, diagnoses the most likely misconception, and responds with a question or hint at the lowest level of help that is likely to unblock the student. It escalates only when the student remains stuck, and it never outputs a complete solution. Tutors see a live summary of which misconceptions are occurring in the room.

The expected value is faster unblocking during labs, reduced repetitive load on tutors and a learning interaction that preserves productive struggle.

## 2. Introduction and Background

### 2.1 Application Context

Our context is a first-year Python unit with weekly two-hour labs. Each lab contains four to six short exercises with automated tests. Students work in a browser-based editor provided by the unit, and tutors circulate to help.

### 2.2 Evidence that the Problem Exists

Novice programmers spend a large share of their time interpreting error messages, and unhelpful error messages are a well-documented barrier in introductory programming (Becker et al., 2019). Studies of help-seeking in labs show that students often wait several minutes for tutor assistance, and that many do not ask at all (Denny et al., 2024). Tutors in our own unit, consulted informally, reported that roughly half of help requests concern the same handful of issues each week.

### 2.3 Current Practice and Existing Tools

Students currently rely on tutors, discussion forums and, increasingly, general AI chat assistants. Automated test feedback tells a student *that* a test failed but not *why*. Enhanced compiler error messages help with syntax but not with logic errors (Becker et al., 2019).

### 2.4 Learning Design Principles

Three principles from computing education research shape the design. First, **productive struggle**: novices learn more when they work through a difficulty with appropriate support than when they are shown the answer, provided the struggle does not tip into disengagement. Second, **graded assistance**: effective tutors start with the least help that might work — a question that redirects attention — and add detail only when needed. Third, **error-message literacy**: many novice difficulties are not conceptual but interpretive; the student does not know what the error message is telling them (Becker et al., 2019). Enhanced explanations of error messages generated by language models have been shown to be understandable to novices in many cases, although quality varies (Leinonen et al., 2023).

These principles imply that the system should (a) diagnose before it helps, (b) control the level of help explicitly, and (c) treat the student's own code and error output as the primary context rather than a generic description of the topic.

### 2.5 What Tutors Do Today

When a tutor reaches a stuck student, a typical interaction has four moves: the tutor asks what the student expected to happen, asks them to point to where the behaviour diverges, names the concept involved, and only then suggests a change. Tutors we consulted described the first two moves as the most valuable and the most time-consuming, because they require reading the student's code from scratch each time. CodeCoach is designed to perform these first moves consistently, so that tutor time is reserved for students who need a conversation rather than a pointer.

## 3. Problem Statement and Motivation

### 3.1 Specific Problem

During labs, students who are stuck on a logic or runtime error wait too long for help, and when they turn to general AI tools they often receive complete solutions that remove the learning opportunity.

### 3.2 Who Is Affected

First-year students, especially those with no prior programming experience; lab tutors, who handle repetitive questions; and unit coordinators, who need insight into common difficulties.

### 3.3 Why the Problem Matters

Early disengagement in introductory programming is associated with failure and withdrawal. Unblocking students quickly, without doing the work for them, is the central pedagogical challenge of lab support.

### 3.4 Why Generative AI Is Appropriate

Diagnosing a novice's misconception from their code, the exercise specification and an error trace requires flexible reasoning over code and natural language. Rule-based hint systems require hand-authored rules for every exercise and fail on unanticipated mistakes. Large language models can generate explanations of code and errors that novices find helpful (Leinonen et al., 2023), but unconstrained they also give away answers. A constrained agent that controls the level of help is therefore both necessary and distinct from a chat assistant.

### 3.5 Objective

Build a working hint agent integrated with one week's lab exercises, with graded hint levels, solution-leak prevention and a tutor dashboard.

## 5. Proposed Product and Innovation

### 5.1 Product Concept

CodeCoach adds a "Hint" button to the lab editor. When pressed, the agent gathers context, diagnoses the problem and returns a hint at the current level. Each further press for the same exercise raises the level: level 1 asks a guiding question, level 2 points to the relevant line or concept, level 3 explains the fix in words but still without writing the code.

### 5.2 AI Components

1. **Context builder** assembles the specification, tests, student code and last output.
2. **Diagnosis step** asks the model to name the most likely misconception from a fixed taxonomy of 18 common novice errors, adapted from the literature on novice misconceptions.
3. **Hint generator** produces a hint at the requested level, conditioned on the diagnosis.
4. **Leak checker** compares the hint with the reference solution (token overlap and code-block detection) and regenerates once if the check fails; if it fails again, a fixed level-appropriate message is shown.

### 5.2a Misconception Taxonomy

The diagnosis step selects from a fixed taxonomy so that hints and tutor analytics use consistent categories. The initial taxonomy is:

| Code | Misconception | Typical symptom |
|---|---|---|
| M1 | Printing instead of returning | Test receives `None` |
| M2 | Off-by-one loop bounds | Last element missing or index error |
| M3 | Modifying a list while iterating | Elements skipped |
| M4 | Integer vs float division | Unexpected truncation |
| M5 | Variable scope confusion | `NameError` or unchanged outer variable |
| M6 | Shadowing a built-in name | `TypeError: 'list' object is not callable` |
| M7 | Mutable default argument | State persists across calls |
| M8 | String vs number comparison | Comparison always false |
| M9 | Missing base case in recursion | `RecursionError` |
| M10 | Assignment vs equality | Syntax error or wrong branch |
| M11 | Early return inside loop | Only first item processed |
| M12 | Misreading the specification | Output format differs from expected |
| M13 | Indentation changes control flow | Statement runs once instead of per iteration |
| M14 | Uninitialised accumulator | Wrong totals |
| M15 | Confusing index and value | Wrong element used |
| M16 | Incorrect boolean logic | Condition inverted or too broad |
| M17 | Input parsing errors | `ValueError` on conversion |
| M18 | Other / unclear | Escalate to tutor suggestion |

### 5.2b Hint Levels

| Level | Purpose | Form | Example constraint |
|---|---|---|---|
| 1 | Redirect attention | A question about expected vs actual behaviour | No line numbers, no code |
| 2 | Locate | Points to the relevant line or concept | May name the line; no corrected code |
| 3 | Explain the fix in words | Describes what to change and why | Never writes the corrected statement |

### 5.3 Distinction from a Generic Chatbot

A chat assistant answers whatever is asked, usually with full code. CodeCoach controls the level of help, grounds the hint in the exercise's own tests, checks every hint against the reference solution before display, and aggregates misconceptions for tutors.

## 6. Methodology and System Design

### 6.1 Architecture

The lab editor (existing unit platform) calls a small FastAPI service. The service holds the exercise catalogue, calls the model for diagnosis and hint generation, runs the leak checker, and writes to a PostgreSQL log that also feeds the tutor dashboard (Appendix A).

### 6.2 Model Strategy

We will use a hosted model at low temperature for diagnosis (structured output over the taxonomy) and slightly higher temperature for hint wording. Prompts include two worked examples per hint level.

### 6.3 Development Method

Scrum with two-week sprints, a shared backlog and weekly stand-ups. Each sprint ends with a demo to the group.

### 6.4 Data and Tools

Exercises and reference solutions come from the unit's public lab sheets. Student code for development will be written by our group to imitate typical mistakes. Tools: Python, FastAPI, PostgreSQL, React, a hosted LLM API.

### 6.5 Prompt Design and Context Limits

The diagnosis prompt contains the exercise specification, the names and messages of failing tests, the student's code with line numbers and the taxonomy with one-line definitions. It asks for a JSON object with the misconception code, the line numbers involved and a one-sentence justification. The hint prompt receives the diagnosis, the hint level and the level's constraints, plus two worked examples at that level. Student code longer than 200 lines is truncated around the lines referenced by the failing test's traceback; in our exercises no solution exceeds 60 lines, so truncation is expected to be rare.

### 6.6 Leak Checking in Detail

The leak checker has two parts. A structural check rejects any hint containing a fenced code block or more than one line that parses as Python. A similarity check tokenises the hint and the reference solution and rejects hints whose overlap with the solution's identifier and operator sequence exceeds the threshold. Both checks are deterministic and logged, so that every blocked hint can be inspected.

### 6.7 Tutor Dashboard

The dashboard lists students in the lab session ordered by time since their first hint request on the current exercise, with the current hint level and the diagnosed misconception. A summary panel shows misconception counts per exercise for the session, which tutors can use to decide when a short whole-class explanation would be more efficient than individual help.

## 7. Business and Product Analysis

### 7.1 Value Proposition

CodeCoach helps students get unstuck and helps tutors focus their time.

### 7.2 Users and Customers

Students and tutors in introductory programming units; the customer would be the faculty's teaching support team.

### 7.3 Alternatives

We are not aware of another tool that offers graded hints for lab exercises, so CodeCoach fills a clear gap.

### 7.4 Feasibility and Costs

The service is small and the model calls are short, so cost per hint will be low. The unit platform already supports embedding a button in the editor.

## 8. Evaluation Plan

We will evaluate CodeCoach by demonstrating it to our classmates and tutor in Week 12 and collecting their feedback. After using the hint button on a few exercises, participants will complete a short survey asking whether the hints were helpful and whether they would use CodeCoach in their labs.

The project will be considered successful if most participants find the hints helpful and the demo runs without errors. We will also look through the hint logs to check that hints look reasonable.

## Appendix B — Example Interactions

A student's function returns `None` because it prints the result instead of returning it. Level 1: "Your test expects a value back from `average()`. What does your function give back to the caller right now?" Level 2: "Look at the last line of `average()`: it displays the result. Is displaying the same as giving it back?" Level 3: "Replace the line that displays the result with one that returns it, then run the tests again."

A second student's loop `for i in range(1, len(scores))` misses the first score. Level 1: "Which positions in the list does your loop visit? Try printing `i` on each pass." Level 2: "The loop starts at position 1. Where does a Python list start?" Level 3: "Change the start of the range so the first position is included."

## Appendix C — Diagnosis Output Contract

The diagnosis step must return `{"code": "M1".."M18", "lines": [int], "justification": str}`. Outputs that do not parse, or that name a code outside the taxonomy, are retried once and otherwise mapped to M18, which produces a level-1 hint suggesting the student ask their tutor.
